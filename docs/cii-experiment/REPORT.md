## 3. Implementation

**Boundary.** No UI, server, PDF, authentication or persistence work. No change to the profile, the semantic model or
the monetary engine. No dependency added.

**XML and parser decision.** No dependency. The serializer builds XML the same way `ubl.ts` does (a small element
tree and a renderer). Extraction, structural checks and mutations use the existing strict test reader
`tests/support/xml.ts`, extended with a renderer that writes a parsed tree back in the serializers' exact layout.
Mutations are applied to the parsed tree and rendered back; the run asserts `render(parse(xml)) === xml` before any
mutation, so a control changes only the elements it names. Reasons:

- The generated XML is a constrained, deterministic subset (elements, attributes, five entities). Reading it needs
  path selection over literal names, which the reader already does. Namespace correctness of the prefixes is checked
  separately on the root element.
- Well-formedness, namespaces and XSD validity in the full sense are established by KoSIT, not by the reader.
- A dependency would change `package-lock.json`, which the manifest records and `npm test` checks (see §9, O-1).

Ceiling: the reader matches names by literal prefix, not by namespace. That is sufficient for output the project
generates itself and is not a general XML parser.

**Serializer.** `src/lib/domain/xrechnung/cii.ts`, `serializeCiiInvoice(invoice: Invoice)`. It accepts only an
object produced by `buildInvoice` (`isValidatedInvoice`), the same object the UBL serializer consumes. Element order
follows the CII D16B XSD of the pinned configuration; paths follow SeMoX (binding `cii`).

**No monetary calculation in the serializer.** Every amount is a `Decimal` from the engine, formatted only by
`formatXmlDecimal`. `cii.ts` imports no engine function, only types and `formatXmlDecimal`; the existing AST guard
(no arithmetic operators, no `Decimal.units`/`scale`, no floating-point route) now runs on `cii.ts` as well and
passes. The two non-monetary transformations are the date lexical form (`YYYY-MM-DD` → `YYYYMMDD`, removal of `-`)
and `String(index + 1)` for BT-126, which is the preregistered MODEL-U candidate of §9 (see §8 below).

**Provenance.** `cii.ts` and the experiment tooling cite MDR-16 in their header comments; the implementation commits
cite it in their bodies. No preregistration file was touched to add a citation.

**Other changed files.** `tools/kosit/validate.ts` exports its validator runner and tooling preparation and runs its
own `main` only when executed directly (UBL harness behaviour unchanged, re-run: 4 PASS and the control rejected).
`tests/support/static-checks.ts` also confines CII names to `cii.ts`. New: `tests/support/projection.ts`
(projection, comparator, money comparison, structural checks, mutation helpers), `tools/cii-experiment/experiment.ts`
(layers 2 and 3, controls and probes), `tools/cii-experiment/run.ts` (layer 1 and the result file),
`tests/domain/xrechnung-cii.test.ts`.

**SER history.** No SER finding occurred: the first KoSIT run of the first CII output was ACCEPT for all eight
fixtures and the first layer-2/3 run showed no difference. Two defects were found and fixed during implementation,
both in experiment tooling, neither in the serializer nor in any output under test: a test helper that picked the
first `DateTimeString` in reverse document order (it mutated BT-9 where the test meant BT-2), and a TypeScript typing
error in `run.ts`. Neither is a §9 finding.

**MODEL-U** (all three are the preregistered candidates; reported, not moved):

- **MODEL-U-1:** BT-23 and BT-24 are protocol constants held in each serializer (`ubl.ts` and `cii.ts`), not by
  `Invoice`.
- **MODEL-U-2:** BT-126 is derived as input index + 1 in each serializer.
- **MODEL-U-3:** the VAT tax scheme is a constant in each serializer: UBL `cac:TaxScheme/cbc:ID` = `VAT` (BT-31,
  BG-23, BG-30); CII `ram:TypeCode` = `VAT` (BG-23, BG-30) and `@schemeID` = `VA` on BT-31.

**Preregistered source-limitation and binding items, the limitation list required by EO 6** (§15; recorded before
execution, not §9 findings of this experiment):

- **SRC-1, preregistered §15 source-limitation item:** CEN/TS 16931-3-2 and 16931-3-3 are not available. Every
  binding rests on SeMoX, the KoSIT XSD and Schematron. It supports the preregistered statement that MDR-14 level (b)
  is INSUFFICIENT (SRC). It is not a §9 finding against any MDR-16 outcome.
- **SRC-2, preregistered source-limitation / source-discrepancy item resolved by runtime observation for the pinned
  configuration:** SeMoX says R120 could not yet be implemented for CII, while the XRechnung CII Schematron contains it
  (wf_fa1kxd); §15 and §11 required runtime observation to decide the behaviour. Observed with configuration
  2026-08-31: R120 is enforced as a warning in UBL and CII, present in P1 and absent in P0 and P2 (§6). This resolves
  the runtime question for this pinned configuration only; it says nothing about CEN/TS 16931-3-x or about CII
  behaviour in general, and the SeMoX statement itself is unchanged. It is not a §9 finding against EO 5.
- **BIND (preregistered):** BT-41 (`PersonName` | `DepartmentName`) and BT-84 (`IBANID` | `ProprietaryID`) have two
  admissible SeMoX bindings; the frozen project choices were implemented and verified structurally. No new evidence
  showed either choice to be unsupported, so there is no preregistration deviation and no BIND finding.

**VAL-1:** KoSIT accepts M1 (BT-117 of the 7 % bucket is 3.54 instead of 3.53, totals coherent) in both syntaxes with
no message. This is validator tolerance, known in §15 (for example BR-CO-17), with no prediction made and no conflict
with MDR-13: the monetary oracle rejects M1. It confirms that validator acceptance is not monetary evidence.

**Observations (not §9 findings):**

- **O-1:** §12 of the protocol and the header of `tools/cii-experiment/manifest.ts` say the `recorded` identities are
  not enforced by `npm test`. The test compares the whole generated manifest, so `npm test` does enforce them
  (`ubl.ts`, `package-lock.json`, `.node-version` and the protected sources). This did not affect any result. It
  constrained the implementation: no dependency and no refactoring of `ubl.ts` during the experiment (the renderer is
  duplicated in `cii.ts` for that reason, marked for later extraction).
- **O-2:** In L3 the UBL run additionally reports UBL-DT-01; the CII run reports BR-DEC-23 only. Both are errors on
  the probed amount; the expectation (XSD valid, BR-DEC-23 error) holds in both syntaxes. UBL-DT-01 is outside the
  frozen rule inventory for the probed term: `rule-inventory.json` lists it only under BT-146, not under BT-131. It is
  disclosed here and does not change the seven MDR-16 evaluations.
- **O-3:** Schematron does not run after an XSD failure (L1, L2, and the V2 wrong-scenario runs have fewer steps).
  For V2 this is part of the WRONG-SCENARIO class. For L1 and L2 it means the complete preregistered evidence path is
  not observed, which is why MDR-14 level (a) is INSUFFICIENT (§9).
